## Execution order and release gates

1. Complete available security and correctness work first. Reconcile the database before shipping transactions that depend on unverified tables or functions. A migration file alone does not establish production safety.
2. Ship focused PRs against current main; inspect active branches and open PRs before claiming an item. Never overwrite another session's work. Run regression tests appropriate to the changed behavior, type check, lint and production build; use CI as the merge gate.
3. Main is deployed through existing Vercel Git integration. Check the deployment status and changed public behavior. Distinguish merged, deployed and end-to-end verified. Respect rate limits and batch changes.
4. Keep database, payment sandbox and signed-in/email journey tests explicitly open until the actual environment is available. Do not use private API bypasses or guess credentials. Supabase access is connected and the production schema can be inspected; the reviewed production permission correction was applied after owner approval; Vercel dashboard connector access previously failed, while GitHub deployment status is available.
5. After every item passes its acceptance criteria, perform a fresh audit across browser, API, data and delivery paths. Convert demonstrated regressions or justified upgrades into new checklist items. Do not produce empty releases merely to keep activity going.
